# 会员健康管理方案系统 — 设计 v2.3 定稿

> 仓库外评审稿，非 git。2026-11-12。
> v2.3 收敛打卡模型：主记录按「一次打卡 × 一个干预」追加式记录，**无唯一约束、无独立明细表**；缺失判定在统计端。
> 迭代脉络：v2(按目标打卡) → v2.1(目标/干预分表+按干预切分) → v2.2(干预级频次) → v2.3(单表追加式打卡) → v2.4(取消目标↔干预关联表：目标与干预各自独立，统计改按干预维度；老 health_goals/health_goal_items 下线) → **v2.5(方案表瘦身：删 `plan_content/cycle_days/ai_draft/ai_status`，周期只留 `duration_days`；AI 改为「生成任务+任务号查询」不落方案表；详情取消派生 `audit_state`，审批信息一律读审批履历)**。

---

## 一、核心理念（一句话）

- **干预 = 打卡字段 = 一次打卡的最小记录单位**。
- 打卡**不做写入端限流/归并**：用户一天打几次都照记，追加式。频次（每日/每周N）只是统计端的"预期值"，用来事后判断"缺了哪几天"。
- 统计口径从"限制当天只能打一次"变为"事后对比频次预期算缺失"。

---

## 二、数据模型（4 张核心表 + 1 审批履历 + 方案扩展）

### 2.1 `health_plans`（既有表，扩展）—— 方案主表
`plan_type`(健康方案)、`health_intent`(管理意向快照)、**`duration_days`(执行周期天数，创建必填)**、`review_remark`(最近一次审批意见，由审核回写)、`start_date/end_date`。
> v2.5 瘦身：**删 `plan_content`**（方案内容只体现在目标项/干预项）、**删 `cycle_days`**（周期只留 `duration_days`）、**删 `ai_draft/ai_status`**（AI 仅是生成草稿的手段，产物与手工创建一致，最终都落到目标/干预）。
状态机：1 草稿(待健管师审核) → 2 健管师通过(待医生确认) → 3 已定稿 → 9 已中止；执行态(待生效/执行中/已完成)由时间窗派生。
**审批进度不落派生字段**：不再返回 `audit_state`，前端用「状态 + 审批履历(action)` 自己组装"待审/被驳回待改"。
**≤5 目标硬校验**在目标写入时做。
**审核期可编辑**：AI 草稿(1)后健管师、健管师通过(2)后医生，在各自审核阶段都可通过 `PUT /plan/{id}` 修改方案内容（含目标/干预增删改）。修改**只更新内容、不改变审批进度**（谁审核谁改，改后落履历+继续流转），不回退已通过的审核步骤。

### 2.2 `health_plan_goals`（新）—— 目标
`plan_id / category(7类) / goal_code / goal_label / goal_basis(依据，文本) / status / sort_order / BaseModel`
唯一 `uk(plan_id, goal_code)`；方案内目标数 ≤ 5。
> `goal_basis` 用简单文本记录该目标的来源和依据（如来自哪项档案异常/就诊记录）。

### 2.3 `health_plan_interventions`（新）—— 干预 = 打卡字段
| 列 | 说明 |
|---|---|
| `plan_id` | 所属方案 |
| `interv_code` | 干预编码（压常量：diet_salt/blood_pressure_daily…） |
| `interv_name` / `action_desc` | 干预名称/描述 |
| `interv_basis` | 依据（文本，记录来源/依据） |
| `field_type` | 1数值/2文本/3布尔/4枚举/5多选 |
| `field_unit` / `metric_code` | 数值单位 / 关联健康指标 |
| `option_json` | 枚举/多选可选项 |
| **`checkin_freq_type`** | **打卡频次：1每日 / 2每周N次** |
| **`checkin_freq_value`** | **每周N次时=N；每日恒1** |
| `required` / `sort_order` / `status` | 必填 / 顺序 / 启停 |
| + BaseModel | 软删 |

### 2.4 `health_plan_checkins`（新，终稿版）—— 打卡记录（单表追加式）
| 列 | 说明 |
|---|---|
| `plan_id` | 所属方案 |
| `member_id` | 会员 |
| **`intervention_id`** | **干预 id（一次打卡的最小单位）** |
| `field_value` | 数值（整数缩放） |
| `value_text` | 文本/布尔/枚举/多选展示值（多选 JSON 数组） |
| `is_abnormal` | 异常标 |
| `checkin_time` | UTC 秒 |
| + BaseModel | 软删 |

**无唯一约束、无独立明细表**：用户一天同一干预打几次就存几条。一条记录 = 一次打卡 × 一个干预。

### 2.5 `health_plan_audit_reviews`（新）—— 审批履历
`plan_id / action(1生成/2健管师通过/3医生通过/4医生驳回/9中止) / operator_id / operator_name / role(ai/healthmgr/doctor) / result(通过/驳回) / remark / operated_at / BaseModel`（创建记录+软删）。
> v2.5：**健管师无驳回动作**（健管师只负责通过；不认可则直接改方案内容后重新提交）；医生驳回 = 方案回落到状态 1 草稿，由健管师修改后重新提交。
用于业务审批时间线的查询留痕（不覆盖，只追加）。

## 三、打卡流程

1. 会员（AI语音一句话 or 表单）一次输入当天做的所有事项："今天量了血压120/79，吃了降压药，快走了30分钟"。
2. 后端按**干预 id 拆成多条**，每条一条 `health_plan_checkins`：血压→intervention A(120/79)、服药→B(布尔完成)、快走→C(30分钟)。
3. **追加写入，不做当天去重/归并**。用户一天打3次同一干预就存3条。
4. 频次是**预期值**，只在统计端读干预表的 `checkin_freq_type/value` 算"应打卡"。

---

## 四、缺失判定 & 统计（统计端，不做写入端限制）

- **应打卡天数**：对每个干预，取频次——每日=周期内每天；每周N=周期内每周N天（按干预表 freq 推导）。
- **实打卡**：`health_plan_checkins` 按 `(plan_id, member_id, intervention_id)` 按天去重统计实际打卡的日期集合。
- **缺失判定**：`应打卡日期集合 - 实打卡日期集合` = 缺了哪些天。例：某干预每周3次，该周应打3天、实际只打了1天 → 缺2天。
- **统计输出**（app会员+staff健管师）：
  - 打卡达成率：按周期累计实打卡/应打卡。
  - 周缺失天数：如"本周缺2次"。
  - 连续打卡天数。
  - 干预对应指标趋势：field_value → metric_records/trend 复用既有接口。
- **聚合维度 = 干预**（v2.4）：不再按目标聚合（目标与干预无关联表），`interv_stats` 按 `intervention_id` 输出应/实/达成率。

## 五、接口（概要）

- `POST /checkin` — 入参 `plan_id + [{intervention_id, field_value, value_text}]` → 追加多条记录。
- `GET /checkin-dued` — 取某日/某周期内各干预的应打卡频次（动态推导）。
- `GET /checkins` — 按日期/干预反显打卡历史。
- `GET /checkin-stats` — 达成率/缺失次数/连续天数/按干预聚合（`interv_stats`）。
- 审核：`PUT /plan/{id}`（**健管师/医生审核期修改方案**，含目标/干预增删改，仅更新内容不改变审批进度）+ `POST /plan/{id}/review`（健管师通过 → 医生通过/驳回；医生驳回令方案回到草稿 1；每次动作追加审批履历，最新意见同时回写方案 `review_remark`）。
- 创建：`POST /members/{id}/plans`（手工创建与 AI 草稿编辑后保存走同一接口，一次保存生成一条方案记录）。

## 六、落地步骤
1. 7类目标 + 干预编码常量收口 common/models。
2. 建 4 张新表（`health_plan_goals`/`health_plan_interventions`/`health_plan_checkins`/`health_plan_audit_reviews`）+ 扩展 health_plans（DDL + gorm model）。
3. 子服务 health：方案/目标/干预（独立维护，无关联表）CRUD + 打卡(追加) + 统计(缺失判定/按干预聚合) + 审核流。
4. AI：复用 /api/v1/app/ai/chat 生成方案草稿（**异步生成任务 + 任务号，前端轮询任务状态取草稿；草稿不落 health_plans，健管师编辑后调 `POST /members/{id}/plans` 保存才产生方案记录**）+ 语音打卡解析成干预字段。
5. 端：app(会员打卡+统计) + staff(健管师审核+统计)。
6. 完成后 GOWORK=off go build → svc.sh restart（output/bin/health、xingfu_gateway）。

## 七、关键设计取舍记录

- **打卡不做写入端限流**：用户超频/补打卡不拦，避免误伤真实行为；靠统计端缺失判定反映真实性。频次只在数据真实性统计里体现"预期vs实际"。
- **主记录即干预最小粒度**：无独立明细表，一条记录=一次打卡×一个干预，模型最简、统计直接。
- **频次放干预表**：每日/每周N混搭，由统计端推导每个干预的应打卡日程。
- **目标/干预带"依据"文本字段**：`goal_basis`/`interv_basis` 简单文本记录来源和依据，不做枚举/引用关联，保持建模轻量。
- **取消目标↔干预关联表（v2.4 调整）**：目标与干预各自独立维护，不再记录多对多关系——方案只有一层「干预」承担打卡与统计，目标仅作为方向说明；好处是编辑目标不影响打卡引用，代价是失去「按目标聚合」维度，统计改按干预维度。
- **审核期可编辑不回退**：健管师/医生在各自审核阶段可 `PUT /plan/{id}` 修改方案内容，修改仅更新内容、审批进度不变，不回退已通过步骤，避免流程过长。
- **方案表不存正文/AI 状态（v2.5 调整）**：方案的"内容"= 目标项 + 干预项，正文一旦冗余存储就必然与结构化项漂移；AI 只是生成草稿的一种方式，产物与手工创建等价，因此 AI 状态属于"生成任务"而不属于业务方案，走独立任务 + 任务号查询，方案表彻底与 AI 解耦。
- **审批信息读履历，不再派生 audit_state（v2.5 调整）**：派生状态需要定期重算且口径易漂移，改为「方案状态 + 审批履历」由前端组装展示，详情接口不再返回审计态。
